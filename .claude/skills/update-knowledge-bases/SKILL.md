# Update the knowledge bases

Four repos share one layout idea (topics + generated index + checks) and one local web app:

| Repo | Topics | Rules | Checks CI runs |
|---|---|---|---|
| `AI-Knowledge-Base` | category folders, frontmatter | `AGENTS.md` | `build_index.py --strict`, `check_code.py`, `manage.py test webapp` |
| `Software-Engineering-KnowledgeBase` | category folders, frontmatter | `AGENTS.md` | `test_build_index.py`, `build_index.py`, `check_code.py` |
| `Cyber-Security-Knowledge-Base` | `kb/NN-area/`, fixed headings | `CONTRIBUTING.md` | `scripts/check-kb.sh`, `bash -n`, `audit.sh` |
| `Brain` | category folders, frontmatter | `AGENTS.md`, `CONTRIBUTING.md` | `ruff`, `build_index.py`, `run_code_blocks.py`, game tests |

Each repo's own rules file wins over this skill on content conventions. Read it before editing that repo.

## 1. Get all repos side by side
Clone any missing repo next to the current one (`git clone https://github.com/faheemkhaskheli9/<repo>`), or
attach it to the session first if the environment needs that. Work on the branch the task names, otherwise a
new topic branch per repo. Then:

```bash
H=.claude/skills/update-knowledge-bases/kb_maintain.py
python3 $H status          # branch, uncommitted files, ahead/behind
python3 $H check           # quick checks in every repo; --full adds topic code and game tests
python3 $H drift           # shared web-app files that differ between repos
```

## 2. Find what needs doing, in this order
1. **Failing checks** and generated files (`INDEX.md`, `llms.txt`) that are out of date.
2. **Open GitHub issues** labelled `bug` or `kb-improvement`, and `ROADMAP.md` items.
3. **Wrong or stale facts**: `build_index.py` stale warnings and `valid-until` markers. Re-check against the
   cited official source; bump `last_verified` only for what you actually re-checked. Never invent versions,
   prices, benchmarks or limits; leave them out instead.
4. **Broken links**: `check_links.py` (AI, SE; needs network), relative links, `[[links]]`.
5. **Structure gaps**: orphan topics, missing `## Related` links, glossary terms with no topic, overview
   topics no scenario links to, missing template sections.
6. **Coverage gaps**: an important topic the base lacks. Add it from the repo's template with runnable code
   and cited sources, and link it from an existing topic.
7. **Tooling bugs** in the build/check scripts or the web app. Add a test with each fix.

## 3. Make the changes
- One logical change per commit, message in the imperative ("Fix ...", "Add ..."), body says why.
- After editing topics, rebuild the index (`python3 build_index.py`) and commit what it writes.
- A bug you find but do not fix: open a GitHub issue labelled `bug` (search for a duplicate first) with symptom,
  repro steps, cause with `file:line`, and a suggested fix.
- Commits, branches, PRs, issues and files carry the repo owner's name only: no tool or assistant names,
  no co-author or "generated by" lines.

## 4. The shared web app (`webapp/`)
`server.py`, `app.js`, `app.css`, `index.html`, `test_server.py` and `screenshots.mjs` are identical in every
repo; `config.json` (title, port, template, header actions, screenshot settings) is per repo. The AI KB also
has a read-only Django site in the same folder.

1. Change the shared files in one repo and run its tests: `python3 webapp/test_server.py`.
2. Copy them to the others: `python3 $H sync-webapp <that-repo>`, then `python3 $H check` and `python3 $H drift`.
3. Try it: `python3 webapp/server.py --open`.
4. Refresh the screenshots once the change is committed (the "Changes" shots list uncommitted files):
   `node webapp/screenshots.mjs` (needs `playwright`; set `SHOTS_OUT=/tmp/x` for a trial run). Look at every
   PNG before committing it.
5. Update the guide in the same change: `docs/app-guide.md` (AI, Cyber), `docs/webapp-guide.md` (Brain),
   `webapp/README.md` (SE). Each feature gets what it does, how to use it and a screenshot.

## 5. Finish
- `python3 $H check --full` where the tools are installed; say which checks were skipped and why.
- Push each repo's branch and open one PR per repo; the PR body lists what changed and the check results.
- Report per repo: what changed, issues filed, what is left.
